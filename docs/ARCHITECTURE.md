# Как устроен бот

Этот документ — для понимания. Читай по частям, возвращайся, когда что-то непонятно.

## Общая картина

```
 ┌──────────┐  Wi-Fi   ┌───────────┐         ┌──────────────── сервер Hetzner ────────────────┐
 │ Станция  │ ───────► │  Облако   │ ◄────── │  bridge ──► mosquitto (MQTT) ──► bot.py ───────┼──► Telegram ──► ты
 │ Oukitel  │          │ Wonderfree│         │  (мост)     («доска объявлений»)   (наш бот)   │
 └──────────┘          └───────────┘         └────────────────────────────────────────────────┘
```

Три программы на сервере, каждая в своём Docker-контейнере («коробке»):

| Программа | Чья | Что делает |
|---|---|---|
| **bridge** (мост) | чужая, [oukitel-portable-bridge](https://github.com/VictorCV-DAM/oukitel-portable-bridge) | Каждые несколько секунд спрашивает облако Wonderfree о состоянии станции и вешает ответы на «доску» |
| **mosquitto** | готовая программа | MQTT-брокер — «доска объявлений». Хранит последние записки и раздаёт их тем, кто подписан |
| **bot** | наша, `bot.py` | Читает записки с доски, отвечает тебе в Telegram, следит за событиями |

### Почему так, а не напрямую?

- Мост уже умеет «разговаривать» со станцией — писать это самим очень сложно (протокол закрыт).
- MQTT разделяет программы: мост ничего не знает о боте, бот — о станции. Можно заменить
  любую часть, не трогая остальные. Например, потом подключить Home Assistant к той же «доске».

### Что такое MQTT-«записка»

Это пара **топик → значение**. Топик похож на путь к файлу:

```
homeassistant/sensor/oukitel/battery       → 67
homeassistant/sensor/oukitel/input_watts   → 350
homeassistant/sensor/oukitel/output_watts  → 120
```

Бот подписан на всё, что начинается с `homeassistant/sensor/oukitel/`. Посмотреть все записки
можно командой `/debug` в боте.

## Файлы проекта

| Файл | Зачем |
|---|---|
| `bot.py` | Весь код бота |
| `store.py` | Хранилище: станции, пользователи, роли, приглашения, настройки сповіщень |
| `history.py` | История показаний (SQLite) и подсчёт статистики: энергия, отключения, пик, время зарядки |
| `requirements.txt` | Список библиотек Python, которые нужны боту |
| `Dockerfile` | Рецепт «коробки» для бота: взять Python, поставить библиотеки, запустить `bot.py` |
| `docker-compose.yml` | Описание всех трёх коробок и как они связаны |
| `mosquitto.conf` | Настройки MQTT-брокера |
| `.env.example` | Образец настроек. Настоящий `.env` с токеном — только на сервере |
| `update.sh` | Скрипт автообновления с GitHub (его запускает cron каждые 5 минут) |

## Что внутри `bot.py`

Файл разделён комментариями вида `# ----- название`. Идём сверху вниз:

### 1. Настройки
Читает файл `.env`: токен бота, кто имеет доступ (`ALLOWED_CHAT_IDS`), пороги уведомлений.
`os.getenv("ИМЯ", "по умолчанию")` — «возьми настройку, а если её нет — вот значение».

### 2. Состояние станции (`StationState`)
Словарь последних значений, например `{"battery": 67, "input_watts": 350}`.
Когда приходит новая записка — `update()` кладёт значение в словарь и запоминает время.
`threading.Lock` нужен, потому что MQTT и Telegram работают параллельно — замок не даёт им
читать и писать одновременно.

### 3. Форматирование (`format_status`)
Берёт словарь и собирает красивое сообщение: заряд, вход, выход, сколько ещё проработает.
Функция `num()` ищет значение под несколькими возможными именами — мост может называть
одно и то же по-разному.

### 4. Расписания
- Хранятся в файле `data/schedules.json` — так они не пропадают после перезапуска.
- `register_jobs()` ставит «будильники» через `job_queue` (встроенный планировщик библиотеки):
  `run_daily` — каждый день в указанное время, `run_repeating` — каждые N минут.

### 5. Команды (`cmd_...`)
Каждая команда — отдельная функция. `/status` → `cmd_status`, `/schedule` → `cmd_schedule` и т.д.
`async def` / `await` — так библиотека умеет обрабатывать много сообщений одновременно,
не дожидаясь, пока закончится предыдущее.

### 6. Кнопки
Два вида:
- **Нижнее меню** (`ReplyKeyboardMarkup`) — кнопки вместо клавиатуры. Нажатие = обычное
  текстовое сообщение «📊 Стан», его ловит `on_menu_text`.
- **Кнопки под сообщением** (`InlineKeyboardMarkup`) — у каждой есть скрытая метка
  `callback_data`, например `sch:t:09:00` («расписание: переключить время 09:00»).
  Нажатие ловит `on_button` и по метке понимает, что делать. Сообщение при этом не новое,
  а редактируется (`edit_message_text`).

### 7. Уведомления (`device_events`, `check_alerts`)
Раз в 15 секунд для каждой станции:
1. `device_events()` сравнивает состояние с прошлым и возвращает **события** (свет появился/пропал, заряжена, ошибка, нет данных).
   Одно событие — одна запись, независимо от того, сколько людей подписано.
2. `check_alerts()` для каждого человека с доступом смотрит его настройки (`Store.notify`) и отправляет только то, что он включил.
   «Низкий заряд» считается отдельно для каждого человека, потому что у всех свой порог.

Защита от спама — «взведение» (гистерезис): после сообщения событие снова срабатывает, только когда показатель отошёл
от порога (заряд ≥ порог+5% / упал до 95%), а не при каждом колебании на 1–2%.
Свет определяет `grid_signal()` по входу, нагрузке и заряду (флага «есть сеть» и режима ДБЖ станция не отдаёт): есть вход из сети → свет есть;
входа нет, а нагрузка есть → живём от батареи; нет ни входа, ни нагрузки → смотрим, не просел ли заряд ниже лимита; иначе «неопределённо»
и остаётся последнее известное. Подробности и пороги — в `CHANGELOG.md` и `.env.example`.

### 8. MQTT (`start_mqtt`)
Подключается к брокеру, подписывается на топики, каждую новую записку отдаёт в `STATE.update`.
Работает в отдельном потоке и сам переподключается при обрыве.

### 9. Запуск (`main`)
Связывает всё вместе: «команда `/status` → функция `cmd_status`», запускает MQTT и бота.

## Пользователи, роли и несколько станций (версия 2)

Всё хранится в `data/store.json`, работой с ним занимается `store.py`:

```
devices: { "main": {имя, топик MQTT}, "mama": {...} }
users:   { chat_id: {имя, admin?, access: {"main": "owner", "mama": "guest"}, расписание} }
invites: { код: {роль, станции, срок} }       # одноразовые ссылки
```

- **Роль считается функцией `Store.role(chat_id, device)`**: админ → всегда «admin», иначе то, что записано в `access`.
- **Приглашение**: `/invite` → бот делает ссылку `t.me/<бот>?start=inv_КОД` → человек нажимает → `cmd_start` находит
  код, добавляет человека и сразу удаляет код (поэтому повторно он не сработает).
- **Несколько станций**: у каждой своя `StationState` в словаре `STATES`; MQTT-сообщение попадает «к своей» станции
  по префиксу топика (`device_for_topic`). Мост на каждую станцию публикует в свой топик (`topic_base` в его `config.json`).
- **Названия**: у станции есть «официальное» имя (`name`: его бот находит в журнале моста по строке `Power station detected: …`
  и сопоставляет по коду устройства = MAC, либо его вручную задаёт админ `/devname`; ручное сильнее) и постоянный номер `index`.
  В MQTT мост шлёт только шаблонное имя, поэтому его не используем; из описания устройства берём серийный номер. У пользователя могут быть личные названия (`aliases`) — их видит только он.
  Итоговое имя для человека даёт `Store.label(chat_id, device)`: личное → иначе настоящее (с номером, если у него две одинаковые).
- **Миграция**: при первом запуске v2 (нет `store.json`) расписания переносятся из `schedules.json`; старый файл не трогается.

## Экраны и навигация (версия 2)

Каждый раздел — функция `*_view(...)`, которая возвращает пару `(текст, кнопки)`. Одну и ту же «страницу» можно показать
новым сообщением (нижнее меню, команды) или заменить текст в уже отправленном сообщении (кнопки под сообщением).
Метки кнопок: `m:<раздел>` — главное меню и разделы, `st:<id>` / `sd:<id>` — короткий и детальный стан, `ren:`/`dn:` — переименование,
`sch:` — расписание, `inv:`/`usr:` — приглашения и пользователи (только админ).
`cu:` / `cx:` / `cy:` / `cn:` / `cl:` / `cli:` — управление (открыть, команда, подтвердить, отмена, лимит заряда), `sp:` / `sx:` — статистика
(станция, период), `nm:` — время итога дня.

## Управление (версия 2, этап 4)

`start_action()` проверяет права, «не больше одной команды на станцию» (словарь `PENDING`), свежесть данных и `availability`,
затем `send_command()` публикует `<база>/<ключ>/set` в MQTT (клиент хранится в `MQTT_CLIENT`). Задача `check_pending` каждые 2 с
сравнивает состояние станции с запрошенным: совпало — «Готово» и кнопки снова доступны, прошло `CONTROL_TIMEOUT_S` — сообщение о неудаче.

## Статистика и итог дня (версия 2, этап 5)

Задача `sample_history` каждые 30 с пишет в `data/history.db` (таблица `samples`: заряд, вход, выход, наличие сети), события света
пишутся в `events` из `check_alerts`. `history.compute_stats()` интегрирует мощность по времени (пропуски длиннее 90 с не считаются),
собирает отключения из пар «пропал → появился» и находит сессии зарядки. `send_summaries` (каждые 30 с) присылает итог дня в выбранное время.

## Как попадает обновление на сервер

```
Claude/ты меняете код → push в GitHub (main) → cron на сервере раз в 5 минут → update.sh
   → git скачивает новую версию → docker compose пересобирает коробку бота → бот перезапущен
```

Файлы `.env`, `data/`, `oukitel-portable-bridge/` git не трогает — они в `.gitignore`.
